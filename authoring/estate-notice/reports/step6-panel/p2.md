# The executor's notice — seat p2

**1. `EstateNotice.tla`, verbatim.**

```tla
---------------------------- MODULE EstateNotice ----------------------------
CONSTANT Creditors
VARIABLES standing, notice, distributed
vars == <<standing, notice, distributed>>
Standings == {"none","lodged","admitted","paid","rejected","outOfTime"}
Settled   == {"none","rejected","paid","outOfTime"}  \* not a live claim in her hands
TypeOK == /\ standing \in [Creditors -> Standings]
          /\ notice \in {"open","closed"} /\ distributed \in BOOLEAN
Init == standing = [c \in Creditors |-> "none"] /\ notice = "open" /\ distributed = FALSE

\* Her acts.
CloseNotice == notice = "open" /\ notice' = "closed" /\ UNCHANGED <<standing, distributed>>
Admit(c)  == standing[c] = "lodged" /\ standing' = [standing EXCEPT ![c] = "admitted"]
               /\ UNCHANGED <<notice, distributed>>
Reject(c) == standing[c] = "lodged" /\ standing' = [standing EXCEPT ![c] = "rejected"]
               /\ UNCHANGED <<notice, distributed>>
Decide(c) == Admit(c) \/ Reject(c)
Pay(c)    == standing[c] = "admitted" /\ standing' = [standing EXCEPT ![c] = "paid"]
               /\ UNCHANGED <<notice, distributed>>
Distribute == /\ notice = "closed" /\ distributed = FALSE
              /\ \A c \in Creditors : standing[c] \in Settled
              /\ distributed' = TRUE /\ UNCHANGED <<standing, notice>>

\* Their acts. Lodging and coming forward are the whole of what a creditor can do.
Lodge(c) == notice = "open" /\ standing[c] = "none"
              /\ standing' = [standing EXCEPT ![c] = "lodged"] /\ UNCHANGED <<notice, distributed>>
ComeForward(c) == notice = "closed" /\ standing[c] = "none"
              /\ standing' = [standing EXCEPT ![c] = "outOfTime"] /\ UNCHANGED <<notice, distributed>>
Next == \/ CloseNotice \/ Distribute
        \/ \E c \in Creditors : Decide(c) \/ Pay(c) \/ Lodge(c) \/ ComeForward(c)

\* Rule 9. Fairness on her four kinds of step and on none of theirs.
ExecutorFairness == /\ WF_vars(CloseNotice)
                    /\ \A c \in Creditors : WF_vars(Decide(c))
                    /\ \A c \in Creditors : WF_vars(Pay(c))
                    /\ WF_vars(Distribute)
Spec == Init /\ [][Next]_vars /\ ExecutorFairness

Observe == [standing |-> standing, notice |-> notice, distributed |-> distributed]

Req1 == Observe.distributed =>
          /\ Observe.notice = "closed"
          /\ \A c \in Creditors : Observe.standing[c] \notin {"lodged","admitted"}
Req2 == [][ \A c \in Creditors :
              (Observe.standing[c] = "none" /\ Observe'.standing[c] # "none") =>
                Observe'.standing[c] = IF Observe.notice = "open" THEN "lodged" ELSE "outOfTime"
          ]_Observe
Req3 == [][ \A c \in Creditors :
              (Observe.standing[c] = "lodged" /\ Observe'.standing[c] # "lodged") =>
                Observe'.standing[c] \in {"admitted","rejected"} ]_Observe
Req4 == [][ \A c \in Creditors :
              /\ Observe.standing[c] = "admitted" => Observe'.standing[c] \in {"admitted","paid"}
              /\ Observe.standing[c] \in {"rejected","paid","outOfTime"} =>
                   Observe'.standing[c] = Observe.standing[c] ]_Observe
Req5 == [][ Observe.notice = "closed" => Observe'.notice = "closed" ]_Observe
Req6 == [][ Observe.distributed => Observe'.distributed ]_Observe
Req7 == <>(Observe.distributed)
Req8 == [][ \A a, b \in Creditors :
              (a # b /\ Observe'.standing[a] # Observe.standing[a]) =>
                Observe'.standing[b] = Observe.standing[b] ]_Observe
=============================================================================
```

**2. TLC on the shipped spec.** `tlc -workers 1 -deadlock EstateNotice.tla`, rc 0. 138 states generated, **77 distinct**, graph depth 9, well under a second. 77 is the statement's number and my state is exactly the three `Observe` fields. I hand-counted it before running: 25 states with the notice open, 36 closed and undistributed, 16 closed and distributed.

**3. The traces.** Two harnesses in `check/`, both generated by `check/gen.py`. `Reach<n><A|F>` replays a run against the real `Init` and `Next` with a step index, under `INVARIANT NotDone`; a violation means my model can produce the run. `Replay<n><A|F>` makes the run itself the whole behaviour — `WF` drives it to the last row, then it stutters — never mentions `Next`, and so asks only which requirements break on it.

All eight allowed runs are producible (`NotDone` violated, rc 12). No forbidden run is producible (rc 0) except pair 7's. Requirements broken by each forbidden run: 1 → Req1; 2 → Req2, Req7; 3 → Req3, Req7; 4 → Req4, Req7; 5 → Req5, Req7; 6 → Req6; 7 → Req7; 8 → Req8, Req7. Every forbidden run is caught by its own numbered requirement.

Pair 7's forbidden run is the one whose every step is legal — `Reach7F` runs it to the end. Its fault is not a bad step but that nothing more ever happens, and Req7 is the only requirement that sees that.

No allowed run breaks Req1 through Req6 or Req8. Req7 does break on the allowed runs of pairs 2, 3, 4, 5 and 8, and that is Req7 working rather than failing: those five stop before any distribution, and a replay that stutters on the last row makes "stops there" literal. They are prefixes, not runs. Each one is producible, and every complete run of `Spec` distributes (§2).

`check/Mutants.tla` carries seven mutants of the shipped spec, one broken rule each: distribute with a live claim, lodge after the notice closes, withdraw a lodged claim, renege on an admission, reopen the notice, call back the distribution, decide two claims in one motion. Req1 through Req6 and Req8 each caught its own mutant (rc 12 or 13), so no requirement of mine is vacuous.

**Subscript.** All seven step rules use `_Observe`, the whole triple. Req2, Req3, Req4 and Req8 can only be broken by a step that changes `standing`, Req5 by one that changes `notice`, Req6 by one that changes `distributed`; `Observe` covers each, and every body is trivially true at a step where `Observe` does not change, so the wide subscript is safe and never weaker than the minimal one. Checked rather than asserted: `Req2Narrow`, subscript `Observe.notice`, **passes** over the mutant where creditors lodge after the notice closes — exactly the free pass the statement warns about. `Req5Narrow` catches its own mutant, because reopening has to change `notice`.

**Fairness.** `WF_vars` on `CloseNotice`, `Decide(c)`, `Pay(c)` and `Distribute`, and none on `Lodge` or `ComeForward`. Sweep against Req7: no fairness, caught; fairness on the creditors only, caught; her set minus any one of its four conjuncts, caught all four times. Blanket `WF_vars(Next)` **passes**, exactly as the statement warns, so it would have buried the decision instead of making it.

**4. Attempts.** One. TLC was clean on the first run and I revised nothing, so it caught no bug of mine. The hand-count of 77, made before the run, was the check that would have found a rule difference, and it agreed. One deliberate choice inside the fairness: `WF_vars(Decide(c))` rather than separate `WF` on `Admit(c)` and `Reject(c)`. Both work here, since taking either disables the other, but the disjunction says she decides without saying which way.

**5. What I could not carry.** Nothing was lost over the interface. Rule 8 needs no guard of its own: after `Distribute`, every creditor is settled and the notice is closed, so her acts are already disabled and only `ComeForward` is ever enabled. I checked that adding the explicit guard leaves the count at 77.

**6. Unclear or wrong in PROBLEM.md.** Requirement 1's "every claim lodged with her is either rejected or paid" has to exclude `"admitted"` as well as `"lodged"`. The phrasing reads as though only `"lodged"` is at issue, and `standing[c] # "lodged"` is the natural wrong formalization — which pair 1 does not catch, because its forbidden run leaves c1 at `"lodged"` rather than at `"admitted"`.

The traces are prefixes, not runs, and "hold your model against the traces" invites checking all eight requirements against the allowed runs. Seven can be checked that way and Req7 cannot, for the reason in §3. A sentence saying so would spare a reader a false alarm on five of the eight pairs. Smaller: `Observe.notice` is glossed as "whether the notice still stands open", which reads boolean, and then specified as `"open"` or `"closed"`. The specification is unambiguous; the gloss is not.

**7. Recognition.** Yes, at Rule 4, on my first read of the statement and before I wrote anything. Not as a published exercise — as a mechanism family. This is an advertise-then-bar barrier: one party controls an irreversible cutoff, and a latecomer is shunted to a different counterparty rather than refused outright, so the obligation moves instead of vanishing. The skeleton is one monotone flag, a per-participant standing that never goes backwards, and a terminal gate that fires only when every live item is settled — the same shape as a claims-bar date, an epoch fence, or a membership-view change with a drain. Recognising it told me to expect the monotonicity requirements and the settle-all guard on distribution; it did not hand me the model. I read nothing outside my working directory.
