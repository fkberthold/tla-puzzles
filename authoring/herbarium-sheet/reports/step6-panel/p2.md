## The last section's two questions

**What the green run establishes.** That the formula parses against my `Observe` and its five field names, so grading will read the interface it expects; that it was evaluated over the whole graph — 259 states, 1103 transitions — rather than skipped; and the one claim it can make, that no step of my model which *changes* `Observe.slips` clears a doubt without a new slip appearing.

**What it fails to establish.** Requirement 5's content is a claim about steps where `doubted` changes. The formula is subscripted `_(Observe.slips)`, so every step that leaves `slips` alone is a stuttering step for it and exempt from the body — and a doubt coming off with no filing leaves `slips` alone by definition. It cannot see the only thing it is about. Worse than blind, it is redundant: if `slips` only grows, which is requirement 3, then any step changing `slips` has `slips' \ slips # {}` outright, so the consequent holds on every step the subscript admits. The shipped requirement 5 is implied by requirement 3 — `TRUE` in a costume, the failure `PROBLEM.md` warns about for requirement 2 two sections earlier.

Evidence, all of it run by me. *A mutant it cannot catch*: `SpecUndoubt` adds `Undoubt(s)`, flipping `doubted[s]` TRUE→FALSE and changing nothing else, and the shipped formula returns `No error has been found`, 1275 generated, 259 distinct, depth 7 (`var-r5-given-vs-undoubt.log`, rc=0). *Widening the subscript catches it*: the identical body under `_(<<Observe.slips, Observe.doubted>>)` gives a four-state counterexample — `Consult(b1,1)`, `Doubt(b1,1)`, `Undoubt(1)`, doubt off with `slips` still `{}` (`var-r5-fixed-vs-undoubt.log`, rc=13). *The fix is not merely stricter*: that widened formula against my own `Spec` returns rc=0 (`var-r5-fixed-vs-mine.log`), so it rejects the mutant and accepts the model. *The redundancy, shown*: `RecordOnlyGrows` against `SpecUndoubt` returns rc=0 (`var-r3-vs-undoubt.log`), so one spec satisfies requirement 3 and the shipped requirement 5 together while clearing doubts with no filing at all.

The sharpest evidence ships in the material. Pair 5's own forbidden run is a behaviour the rules forbid that the formula cannot see. F5, step 3 to step 4:

```
State 3   slips: sheet 1 {}   consulted: 1   reading b1: 1   doubted: TRUE

```

Doubt comes off, no slip is filed, `slips[1]` is `{}` on both sides. The subscript calls the step stuttering and passes it. Checked: `TR5` on w=10 returns `No error has been found` (`tc/tc-10-TR5.log`). My set still rejects F5, by requirement 6 and by `EveryStepIsMine` — never by requirement 5. The requirement does not reject the run its own pair was built around.

## 5. What I could not carry over the interface

The two `PROBLEM.md` names are real. Authorship is invisible — `Observe` shows the record, not the hands in it — so "every step is some botanist's" is not a property of any model here. And rule 3 says a slip carries the stamp it came from where requirement 4 grades only `<=`; my `File` files at exactly `reading[b][s]`, so my model is stricter than the requirement and the requirement cannot see the difference. A third the statement does not name: the shipped requirement 5 carries nothing at all, so rule 6's real content is checked by nothing in the declared set.

One fork I resolved unaided. Rule 6 says a doubtful mark "comes off when a slip is filed on that sheet, whoever files it" — readable as *may* come off or as *always* comes off. My `File` clears it unconditionally, and that reading is what produces 1103/259/7, so I took the numbers as settling it.

## 6. Unclear or wrong in PROBLEM.md

The 259 calibration is wrong as guidance. It is stated as a two-way check — "if your count isn't 259, your rules differ from the rules above" — and it works only one way. Two wrong models reach 259 exactly, per section 4.

The requirement 7 warning is expected but unannounced. A state-level formula under `PROPERTIES` makes TLC print a paragraph recommending `INVARIANT` instead. That is exactly what requirement 7 asks for, but nothing says the warning is coming, and a learner will read it as their own mistake.

Rule 2 leaves one thing implicit: a botanist may re-consult a sheet they already hold, the old stamp lost rather than closed. It matters, because a re-consultation is not a filing and must not discharge the requirement 6 obligation. My `Consult` carries no guard on `reading[b][s]`, which I believe is intended, but the statement never says so outright.

## 7. Mechanism recognition

Yes, and early — reading rule 2, before writing anything. The consultation register is a monotonic counter handed out as a ticket, and the shape is compare-and-set on a version number: read a version, act, and have the write rejected or demoted if the version moved underneath you. `File` moving `accepted` only when `reading[b][s] > MaxStamp(slips[s])` is the compare half, and `SpecStale` is the lost update it exists to prevent. The doubt flag is a dirty bit cleared by the next write. I did not recognise this as any published problem, and I did not look for one.
