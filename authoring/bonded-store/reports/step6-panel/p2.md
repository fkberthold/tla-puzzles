# BondedStore — seat p2

## 1. Properties and cfg, verbatim

Appended below `\* END TRANSLATION`; the system half is untouched, and `BondedStore.tla.orig`
is the shipped file byte for byte.

```tla
OutOfStore == {"released", "movedOn"}

\* Req 1 (INVARIANT).  Both directions at once: released implies paid, and
\* not-entered, in-store and moved-on all imply unpaid.
DutyPaidExactlyOnRelease ==
  \A l \in Lots :
    Observe.dutyPaid[l] <=> (Observe.place[l] = "released")

\* Req 2 (PROPERTY).  Each arm must also permit the lot to stand still: the
\* subscript rules out only steps where the WHOLE of Observe is unchanged, so a
\* step in which some other lot moves is one this formula must accept for this one.
StepsAreLegal ==
  \A l \in Lots :
    /\ (Observe.place[l] = "notEntered")
         => (Observe'.place[l] \in {"notEntered", "inStore"})
    /\ (Observe.place[l] = "inStore")
         => (Observe'.place[l] \in {"inStore", "released", "movedOn"})

\* Req 3 (PROPERTY).  Once out, neither place nor duty changes again.
OutStaysOut ==
  \A l \in Lots :
    (Observe.place[l] \in OutOfStore)
      => /\ Observe'.place[l] = Observe.place[l]
         /\ Observe'.dutyPaid[l] = Observe.dutyPaid[l]

Requirement2 == [][StepsAreLegal]_Observe
Requirement3 == [][OutStaysOut]_Observe
```

`BondedStore.cfg`:

```
SPECIFICATION Spec
CONSTANTS Lots = {l1, l2, l3}
INVARIANT DutyPaidExactlyOnRelease
PROPERTY Requirement2
PROPERTY Requirement3
CHECK_DEADLOCK FALSE
```

## 2. TLC on the shipped spec

`tlc -workers 1 -config BondedStore.cfg BondedStore.tla` → **rc=0**, "No error has been found", **145 states
generated, 64 distinct**, depth 7 (`final.log`) — the count PROBLEM.md predicts. Both `PROPERTY` lines do
register: under this same cfg, mutant `m1` gives rc=12, `m3` 13, `m5` 13.

## 3. Traces and mutants

Not read off by eye. `work/traces/TraceCheck.tla` replays one run as a behavior and pulls my formulas in
through `INSTANCE Reqs`; `work/Reqs.tla` is extracted from `BondedStore.tla` by sed, and a re-extract diffs
clean, so the harness checks the text the grader reads. 10 runs × 3 properties = 30 TLC runs. **Every allowed
run passes all three.** Each forbidden run is caught by exactly the property owning the rule it breaks — the
split PROBLEM.md describes: pair 1 released-and-unpaid → Req 1 (rc=12); pair 2 entry skipped → Req 2 arm 1
(13); pair 3 walked back out of the store → Req 2 arm 2 (13); pair 4 released lot moves on and duty un-pays →
Req 3 (13); pair 5 moved-on-and-paid → Req 1 (12).

Five short runs is weak evidence alone, so I built eight variants of the system half (`work/mutants/`), run
against each property alone. `m0-pristine` rebuilds the shipped `Next` through the same `INSTANCE Reqs`
scaffolding: green on all three at 64 states, which is what says the scaffolding is faithful, not trivially
red. Then, by exit code — `m1` release without paying → Req 1 (12); `m2` moved-on lot pays duty → Req 1 (12);
`m3` release without entering → Req 2 (13); `m4` withdraw to not-entered → Req 2 (13); `m5` released lot moves
on unpaid → Req 3 (13); `m6` moved-on lot pays later with `place` unchanged → Req 1 (12) and Req 3 (13); `m7`
a fifth `place` value from in-store → Req 2 (13). No property is vacuous, and bar `m6` none does another's
job. `m6` also probes PROBLEM.md's subscript warning, tested rather than trusted:
`[][OutStaysOut]_(Observe.place)` returns rc=0 there where the real `[][OutStaysOut]_Observe` returns 13 —
that step changes only `dutyPaid`, and the field subscript reads it as stuttering.

## 4. Attempts, and what changed

**One attempt.** All three passed on the first TLC run at 64 states; TLC caught no bug in my first draft and I
revised no formula. Later edits touched comments and cfg layout only, each followed by a full re-run.
Thinner than it sounds, so here is the guard rail, checked. The trap I expected was reading Req 2 as an
obligation — a not-yet-entered lot *must* move, with no permission to stand still. `work/naive-req2/` holds
that reading, and against the shipped spec it is **violated, rc=13**: one lot sits at not-entered while
another acts. TLC does catch the wrong encoding, so that mistake would have cost one run, not a wrong answer.

One thing moved mid-way, and it was not a property: after the mutant runs this machine's
`edit-after-failure-guard` hook blocked the Write tool, since deliberate rc=12/13 output reads to it as a test
failure. The harness files went in through bash heredocs instead.

## 5. What I could not carry over the interface

Rule 6, "nothing has to happen", is not a safety property and has nothing to write; PROBLEM.md says so, and
`Spec` carries no fairness conjunct. Rule 1's four-way typing is in none of my three as a state predicate. I expected a gap and there is none: from
the fixed `Init`, Req 2 pins every successor of the two live places and Req 3 freezes the two dead ones, so a
fifth value is unreachable. `m7` is that check, and Req 2 catches it — carried transitively, not directly.

Rule 1's "never split, merged or renamed" I did **not** write. It would be `DOMAIN Observe'.place = DOMAIN
Observe.place`, checkable, but both fields' domain is fixed to `Lots` by construction and the requirements
name three properties. A deliberate omission.

## 6. PROBLEM.md

`Places` is defined in the module and used by nothing — not by the translation, not by `Observe`. A dangling
hint that invites `place[l] \in Places`, which is not one of the three requirements.

The block labelled the translation is not what PlusCal emits for that algorithm: a `while (TRUE)` under label
`Keep` yields a `pc` variable and there is none here, so it is hand-trimmed while the `chksum` comment still
claims otherwise. Harmless for the task. Req 2's "when a lot that hasn't been entered yet moves, it moves into the store" reads at first as an
obligation to move. It is not, and PROBLEM.md never says outright that each arm must also permit the lot to
stand still while a different lot acts; its subscript warning points at the neighbouring trap, not this one.
Minor: the traces write `not entered` / `in store` / `moved on` where the module writes `notEntered` /
`inStore` / `movedOn`, the one mapping step nothing states.

## 7. Mechanism family

Recognized early: reading Rule 5, before I opened the module. A per-entity one-way status ledger — each entity
walks a small acyclic set of states, two absorbing, with a boolean pinned by biconditional to exactly one of
them. The same skeleton as an order or a claim moving through a workflow, and Req 3 is the standard "terminal
states are frozen" clause. I do **not** recognize it as a published problem: the customs framing, `Observe` as
the graded interface, and this three-requirement split are not something I have seen, and I did not look.
