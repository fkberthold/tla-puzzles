# Bonded store, seat p1 solve report

## 1. Properties and cfg, verbatim

Added to BondedStore.tla after END TRANSLATION; original kept at orig/BondedStore.tla.

    DutyPaidExactlyOnRelease ==
      \A l \in Lots : Observe.dutyPaid[l] <=> (Observe.place[l] = "released")

    WaysInAndOut ==
      \A l \in Lots :
        /\ (Observe.place[l] = "notEntered" /\ Observe'.place[l] /= "notEntered")
             => Observe'.place[l] = "inStore"
        /\ (Observe.place[l] = "inStore" /\ Observe'.place[l] /= "inStore")
             => Observe'.place[l] \in {"released", "movedOn"}
    WaysInAndOutProp == [][WaysInAndOut]_Observe

    OutStaysOut ==
      \A l \in Lots :
        Observe.place[l] \in {"released", "movedOn"} =>
          /\ Observe'.place[l] = Observe.place[l]
          /\ Observe'.dutyPaid[l] = Observe.dutyPaid[l]
    OutStaysOutProp == [][OutStaysOut]_Observe

BondedStore.cfg:

    SPECIFICATION Spec
    CONSTANT Lots = {l1, l2, l3}
    INVARIANT DutyPaidExactlyOnRelease
    PROPERTY WaysInAndOutProp
    PROPERTY OutStaysOutProp
    CHECK_DEADLOCK FALSE

Reading of the interface: Observe.place[l] carries rule 1's four states as
"notEntered" / "inStore" / "released" / "movedOn"; Observe.dutyPaid[l] is the duty
flag. In requirement 2 I read "moves" as "place changes", and "into the store under
bond" / "moved on under bond" as rule 1's names for the second and fourth state. So
R2 is about place only; the duty side of entry, release and movement is R1's job.

## 3. Per trace pair

Method: for each of the ten runs I generated a module check/PnA.tla or PnF.tla that
EXTENDS BondedStore and walks exactly the listed Observe states (TInit is state 1;
TNext steps i to i+1 and sets place and dutyPaid from a Trace sequence; written by
check/mk-trace.sh). Each run was checked three times, once per property, so the
table shows every property a run breaks, not only the first TLC hits. Sanity: the
distinct-state count equalled the trace length for all ten runs (3,3,2,2,3,3,4,4,3,3),
so no run passed vacuously. rc 12 is TLC's invariant violation, 13 its action
property violation; both came with the matching "Error: ... is violated" line.

    run          | R1 | R2 | R3 | what the violating property saw
    P1 allowed   |  0 |  0 |  0 |
    P1 forbidden | 12 |  0 |  0 | state 3: l1 released, duty unpaid
    P2 allowed   |  0 |  0 |  0 |
    P2 forbidden |  0 | 13 |  0 | step 1->2: l1 notEntered -> released
    P3 allowed   |  0 |  0 |  0 |
    P3 forbidden |  0 | 13 |  0 | step 2->3: l1 inStore -> notEntered
    P4 allowed   |  0 |  0 |  0 |
    P4 forbidden |  0 |  0 | 13 | step 3->4: l1 released -> movedOn, paid -> unpaid
    P5 allowed   |  0 |  0 |  0 |
    P5 forbidden | 12 |  0 |  0 | state 3: l1 movedOn, duty paid

Every forbidden run is rejected by exactly one property, the one its pair was built
for. No allowed run is rejected. This matches what I predicted by hand from the pair files.

Extra check on the subscript warning, which no trace witnesses: mutant
check/MutUnpay.tla adds an action that sets dutyPaid[l] back to FALSE on a released
lot with place unchanged. `[][OutStaysOut]_place` passes it (rc 0, 125 distinct
states); `[][OutStaysOut]_Observe` rejects it (rc 13). The warning is real for R3,
and the Observe subscript is the one that sees the step.

## 4. Attempts and revisions

Two TLC runs on the shipped spec. Run 1: rc 151, "The invariant
DutyPaidExactlyOnRelease specified in the configuration file is not defined in the
specification". Cause: I appended the property block after the module's closing
==== line, so it sat outside the module. Fix: removed the original closing line so
the block sits inside the module. Run 2: rc 0, 64 states. No formula changed between
the two runs or afterwards; the trace harness and the mutant ran as predicted on
their first attempt. TLC caught a placement bug, not a logic bug. Nothing was
revised mid-way.

## 5. Requirements not carried over the interface

None of the three. All three are stated over Observe.place and Observe.dutyPaid
only, and nothing in requirements 1 to 3 needs anything else. Two things in the
rules are not carried and were not asked for: that the keeper is the only actor
(Observe has no actor field, so no formula over Observe can say who moved a lot),
and rule 6, which is the absence of liveness and is respected by adding no fairness
and no "eventually".

## 6. Unclear or wrong in PROBLEM.md

- Nothing wrong: the 64-state count, the -deadlock remark and the module names check out.
- Requirement 2's "moves" is not defined. I took it as a change of place. Under the
  reading "any field changes", the arms would have to say what a duty-only change
  moves "to", which has no meaning. Both readings give the same verdicts on the
  traces, because R1 catches every duty-only fault.
- "Into the store under bond" could also be read as requiring dutyPaid' = FALSE in
  arm 1. I read it as rule 1's name for the state. Same verdicts either way.
- No trace isolates the duty half of R3 (duty of an out lot changing while place
  stays). Pair 4 breaks both halves in one step. So the subscript warning in the
  text is only testable with a mutant, which is why I built one.
- A trap the text could name: properties go after END TRANSLATION, before the closing line.

## 7. Mechanism family

Yes. On the first read of PROBLEM.md, around rule 5, I recognized this as a per-item
one-way lifecycle: a small state machine per lot with one entry state, one middle
state, two absorbing terminal states, and a flag derived from which terminal was
reached. The module's either/or block confirmed it. I did not recognize it as any
specific published problem, and I did not look for one.
