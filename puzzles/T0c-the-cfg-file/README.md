# T0c: The .cfg File — Anatomy and Editing ⭐

**Tier 0 prelude.** No new concept. The goal is to learn the four directives in a `.cfg` file by editing them and watching TLC's behavior change.

## What this puzzle is

A pre-written spec models a clock that ticks up to a maximum, where the maximum is left as a parameter — a `CONSTANT`. The `.cfg` file fills that parameter in and tells TLC what to check. You will run TLC, then edit the `.cfg`, then run TLC again, and notice what changes.

## The spec

Save these two files into a working directory.

`Timer.tla`:

```
---- MODULE Timer ----
EXTENDS Integers

CONSTANT MaxTicks

(*--algorithm Timer {
  variables ticks = 0;

  define {
    TypeOK == ticks \in 0..MaxTicks
  }

  fair process (clk = "Clock") {
    tick:
      while (ticks < MaxTicks) {
        ticks := ticks + 1;
      }
  }
}
*)
====
```

`Timer.cfg`:

```
CONSTANT MaxTicks = 3
SPECIFICATION Spec
INVARIANT TypeOK
PROPERTY Termination
```

## Run it once

From the directory containing both files:

```bash
tlc -pcal Timer.tla
tlc Timer
```

You should see "5 distinct states found" and "No error has been found." The same shape of success as T0a.

## Anatomy of the .cfg

Look at `Timer.cfg`. Four real lines:

```
CONSTANT MaxTicks = 3
SPECIFICATION Spec
INVARIANT TypeOK
PROPERTY Termination
```

Each line is a directive to TLC.

- **`CONSTANT MaxTicks = 3`** — fills in a parameter declared in the spec. Look at the top of `Timer.tla`: `CONSTANT MaxTicks` declares that the spec expects a value but doesn't say what. The `.cfg` is where you choose. Without this line, TLC has no value for `MaxTicks` and won't run.

- **`SPECIFICATION Spec`** — names the temporal formula that defines "what the system does." `Spec` is the symbol pcal generated at the bottom of `Timer.tla` (`Spec == /\ Init /\ [][Next]_vars /\ WF_vars(clk)`). Every TLC run needs exactly one `SPECIFICATION` line.

- **`INVARIANT TypeOK`** — TLC must verify `TypeOK` holds in every reachable state. You can list multiple `INVARIANT` lines; T0b had two.

- **`PROPERTY Termination`** — TLC must verify `Termination` holds across the *behaviors* (sequences of states), not just individual states. `Termination` is auto-generated by pcal and asserts that every process eventually reaches `Done`. Properties live at a different level than invariants — T27 covers that distinction.

Comment syntax in `.cfg` is `\*` (same as TLA+ line comments).

## Experiments

After each edit, re-run `tlc Timer` and look at what changed. **Don't re-run `tlc -pcal`** unless you change `Timer.tla` — the `.tla` file is unchanged across these experiments.

### 1. Comment out an invariant

```
\* INVARIANT TypeOK
```

Re-run. TLC still finishes successfully. State count is the same. The invariant was true anyway, but now TLC isn't checking it. Removing the line doesn't change the spec — it changes what questions you're asking about the spec.

Restore the line.

### 2. Change the constant value

```
CONSTANT MaxTicks = 5
```

Re-run. Now "7 distinct states found." More state space, because the loop runs longer.

Try `MaxTicks = 0`. "1 distinct state" — the loop never enters and the process is immediately Done.

Restore `MaxTicks = 3`.

### 3. Comment out the constant

```
\* CONSTANT MaxTicks = 3
```

Re-run. TLC errors out, something like:

```
The constant parameter MaxTicks is not assigned a value by the configuration file.
```

This is the spec saying "I declared a parameter, you didn't fill it in." Restore the line.

### 4. Comment out the property

```
\* PROPERTY Termination
```

Re-run. Still passes. TLC stops checking the temporal property. Same lesson as #1: removing an assertion does not fix anything; it just stops asking.

### 5. Comment out the SPECIFICATION line

```
\* SPECIFICATION Spec
```

Re-run. TLC errors out — without `SPECIFICATION`, it has no behavior to check. Restore.

## What to take away

- `.cfg` files are TLC instructions, not part of the spec. Editing the cfg never changes what the spec describes — it changes what TLC checks about it.
- Four directives cover most cases: `CONSTANT` (fill in parameters), `SPECIFICATION` (which formula defines the system), `INVARIANT` (state-level claim), `PROPERTY` (behavior-level claim).
- Removing an `INVARIANT` or `PROPERTY` line doesn't fix a violation. It silences the check.
- Removing `SPECIFICATION` or required `CONSTANT` lines causes TLC to refuse to run.

Done. T0d covers the last piece of the toolchain: what `tlc -pcal` actually does to your file.

## Hints

??? hint "💡 Hint 1 — The .cfg is instruction, not specification"
    The .cfg doesn't change what the spec DOES — it changes what TLC CHECKS. Commenting out an invariant doesn't fix a bug; it silences the question. What does changing `CONSTANT MaxTicks = 3` to a different value do to the state space?

??? hint "💡 Hint 2 — Four directives, four purposes"
    The four kinds of lines in a .cfg each do different jobs: CONSTANT fills in unknowns, SPECIFICATION names the system, INVARIANT checks states, PROPERTY checks behaviors. Which of these four are strictly required for TLC to run at all?

??? hint "💡 Hint 3 — The constant flows into the state space"
    When you change `MaxTicks = 3` to `MaxTicks = 5`, the clock runs longer. The loop bound grows. More loop iterations mean more states. That's why "distinct states found" changes — not because the spec changed, but because the parameter TLC is checking with is different.
