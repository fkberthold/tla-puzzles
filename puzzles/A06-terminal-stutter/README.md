# A06: Apalache — Terminal Stutter ⭐

## Lesson: Apalache Hates Deadlocks More Than TLC

When a spec finishes its work — every action's guard becomes false and no transition is possible — TLC says "deadlock." If you don't care about that, TLC offers a `-deadlock` flag to disable deadlock detection if you don't care about terminal states, and pcal generates a `Terminating` clause for you. Apalache also flags deadlock, and just like TLC it considers any state with no enabled action a *deadlock state*. The fix is the same: **make the terminal state stutter**, i.e. add an action that fires when work is done and leaves all variables unchanged.

The general pattern:

```tla
Done ==
  /\ <condition that says "we're finished">
  /\ UNCHANGED vars
```

Then disjunct `Done` into `Next`:

```tla
Next == ActualWork \/ Done
```

`Done` is enabled exactly when `ActualWork` isn't. From the terminal state, behavior loops on `Done` forever — which Apalache (and TLC) reads as "no deadlock; just stuttering." `[][Next]_vars` already permits stuttering, but Apalache's deadlock check asks: "does any reachable state have zero enabled actions?" — `Done` ensures the answer is always no.

A common variant uses an explicit `done` flag:

```tla
\* @type: Bool;
VARIABLE done

Init == ... /\ done = FALSE
Step  == ~done /\ <real step> /\ done' = ...
Halt  == ~done /\ <halt condition> /\ done' = TRUE /\ UNCHANGED otherVars
Done  == done /\ UNCHANGED vars
Next  == Step \/ Halt \/ Done
```

Either way, the lesson is: every reachable state must have at least one enabled action.

**Worked example — a cake-bake.**

A baker mixes ingredients up to a count, then bakes once, then is done. Without `Done`, the spec deadlocks after baking.

```tla
---- MODULE Bake ----
EXTENDS Integers, Apalache

\* @type: Int;
VARIABLE mixes

\* @type: Bool;
VARIABLE baked

vars == << mixes, baked >>

Init ==
  /\ mixes := 0
  /\ baked := FALSE

Mix ==
  /\ ~baked
  /\ mixes < 3
  /\ mixes' := mixes + 1
  /\ baked' := baked

Bake ==
  /\ ~baked
  /\ mixes = 3
  /\ baked' := TRUE
  /\ mixes' := mixes

Done ==
  /\ baked
  /\ UNCHANGED vars

Next == Mix \/ Bake \/ Done

Spec == Init /\ [][Next]_vars
====
```

Trace through it: `mixes` climbs 0 → 1 → 2 → 3 (three `Mix` steps), then `Bake` fires, `baked = TRUE`. Without `Done`, neither `Mix` (guard `~baked` fails) nor `Bake` (guard `~baked` fails) is enabled — DEADLOCK. With `Done`, behavior stays in the final state forever via stutters.

Run TLC without the `Done` line: it reports "Deadlock reached." Add the line back: clean run. Apalache behaves identically on this (modulo the symbolic encoding).

**The key idea.** When you write a finite, terminating spec, ALWAYS add a terminal-stutter action. PlusCal's `Terminating` clause is exactly this pattern, generated by pcal. Pure TLA+ specs don't get it for free — you write it yourself.

## Setup

A simple counter that counts up from 0 to a limit `N`, then halts. We want to express it in pure TLA+ (no PlusCal), with type annotations.

## Task

Write `Counter.tla`:

- `EXTENDS Integers, Apalache`
- One variable: `\* @type: Int;` `VARIABLE n`
- `Init`: `n := 0`
- `Tick`: `n < 5 /\ n' := n + 1`
- A terminal-stutter action `Done`: `n = 5 /\ UNCHANGED n`
- `Next == Tick \/ Done`
- `Spec == Init /\ [][Next]_vars`
- `TypeOK == n \in 0..5`

To see the lesson in action, **first write the spec without `Done`, run TLC, observe the deadlock report, then add `Done` back.**

## Check

Without `Done`:

```bash
cd solution
tlc Counter
```

You should see something like:

```
Error: Deadlock reached.
```

with a 6-state trace ending at `n = 5`.

Now uncomment / re-add the `Done` action and the `\/ Done` disjunct in `Next`. Re-run `tlc Counter` — clean pass, 6 distinct states.

If you have Apalache:

```bash
apalache-mc check --inv=TypeOK --length=10 Counter.tla
```

Apalache reports the same deadlock without `Done`, and accepts the spec with it.

## Expected Result

- Without `Done`: TLC errors out with "Deadlock reached" and a short trace from `n = 0` to `n = 5`.
- With `Done`: 6 distinct states (n = 0, 1, 2, 3, 4, 5), no error. TLC reports "No error has been found." Apalache reports the invariant holds.

## What you learned

- Every reachable state must have at least one enabled action, or the model checker reports DEADLOCK.
- The fix is a stutter action — typically named `Done` — guarded by the terminal condition, with `UNCHANGED vars` as its body.
- Disjunct `Done` into `Next` so it's available from terminal states.
- PlusCal generates a `Terminating` clause that does this for you. In pure TLA+, you write it by hand.

## Hints

??? hint "💡 Hint 1 — The deadlock symptom"
    The lesson says: run TLC on your spec without `Done`. What error does TLC report? The puzzle asks you to observe this error first, then add `Done` to fix it. What should the guard condition for `Done` be?

??? hint "💡 Hint 2 — The stutter pattern"
    `Done` fires when the main work action (`Tick`) can no longer fire. In this spec, `Tick` requires `n < 5`. So `Done` fires when `~(n < 5)`, i.e. when `n >= 5`. What's the simplest form of that condition?

??? hint "💡 Hint 3 — One action, N disjuncts"
    The `Next` formula disjuncts the main action and the stutter: `Next == Tick \/ Done`. This means on every step, either `Tick` (if enabled) or `Done` (if work is finished) is available. With both, no state reaches a deadlock.
