`facility-status/`, `narrator/`, `iam/`, `cloud-state/`, `legacy/`, `ux-services/`
per the commissioning brief. Method: READMEs, design docs, Goa design files, and

## 1. Ranked table of shapes

| 3 | **two-store** (two places must agree) | Structural to the whole cloud/edge split — this platform's central fact is that there are always at least two copies of "the truth" | (a) settings service: `Value` (current) vs `DesiredValue` ("omitted if a change is not in progress"), with `DesiredAt`/`DesiredBy`/`CommandID` linking the pending change back to its originating command (facility-status/services/settings/design/types.go:11,23,37-49,145-147) — and the README states the failure mode explicitly: "the local offline dashboard will continue to process setting updates, and should converge once the [cloud] service becomes available again" (facility-status/services/settings/README.md, Failure Impact section); (b) legacy atlas client keeps "a local cache of configuration and time series data on disk" and is "designed to continue operating in the case of network outage" (legacy/README.md, Atlas Client section); (c) `facilitysync` CLI: "will show differences between YAML and the database (and optionally apply them)" — an explicit diff-then-apply reconciler between a declared file and a live store (legacy/docs/dump-and-sync.md:1-8); (d) narrator's planned `mirror` service: "a consistent agent-side cache of immutable deployment assets", explicitly flagged "not yet designed as of July 2025; RPC interface may change substantially" (narrator/services/deploy/README.md, 2025 Stretch Goal section); (e) cloud-state's whole reason to exist: git-declared `*_VERSION` files reconciled onto live clusters by Flux |
| 4 | **rollout** (versioned config/code across a fleet) | Dominant in cloud-state by design; also present wherever "version" appears in narrator/ux-services | (a) cloud-state: per-cluster `*_VERSION` files pin services to commit SHAs (266 such files across the repo), `*_BRANCH` overrides, `*_LOCK` files freeze a cluster against automated updates, a `PRIMARY=true` flag in `cluster.env` marks the canonical cluster per role, and `scripts/repo_github_matrix` computes which clusters changed under five different modes (`commit/push/pr/all/success`) for selective fan-out (cloud-state/README.md, Version Management System and CI/CD Integration sections; cloud-state/CLAUDE.md:87); (b) ux-services: a site tracks `active_narrator_version` vs `latest_narrator_version` plus a `using_narrator` boolean, i.e. two config-authoring systems (classic CAML and the new narrator system) can be live on the same site simultaneously, and every downstream type is built not to care which one produced it (ux-services/services/front/design/control_config.go:17-30); (c) site-narrative deployment is itself versioned end to end, with a `list_site_narratives` endpoint whose default ordering is "most recent first" and an `include_draft` toggle for whether the unpublished tip counts (ux-services/services/front/design/control_config.go:40-60); (d) ux-services' `loader` routes purely on hostname to serve a "permanent" production S3 prefix or a per-branch "temporary" preview prefix, so many versions of the same frontend can be live at once by convention alone, with no version state beyond "does this S3 prefix exist" (ux-services/services/loader/README.md:15-20) |

## 2. The specific recurring situations

1. A forced I/O point override has a TTL and must revert to automatic control when the TTL lapses; nothing in the design layer states whether an explicit `push_auto_point`/un-force always fires, or whether expiry alone is trusted to hand control back (facility-status/EXECUTIVE_SERVICE_DETAILED.md, `push_force_point`/`push_auto_point`; ux-services point_force.go:55).
2. An agent reporting itself `controlling` must periodically reconfirm before a deadline (`ReconfirmAt`), and the cloud only trusts state updates inside a 6-minute recency window — the interesting question is what happens to "controlling" status during exactly that dead time between a missed reconfirmation and the window expiring (facility-status/services/control-state/service.go:158-169).
3. More than one agent/node can end up reporting `controlling` for the same facility at once; this is treated as detectable-and-alarmable rather than preventable — the system accepts that split-brain can happen and only commits to noticing it after the fact (facility-status/services/control-state/README.md, Multiple-Primary Alarm).
4. A setting has a current value and a separately-tracked desired value that "converge" once a change is in flight; the desired value disappears once convergence completes, but the design doesn't say what happens if the agent never reports the new current value at all (facility-status/services/settings/design/types.go:37-49).
5. A site-narrative deployment must clear a three-part agent approval gate (hardware, strategy/narrative, alarms) before the cloud calls it accepted; each approval is a separate RPC round-trip and any one of them can fail or be skipped, but the deploy README treats the group as a single "critical" block rather than specifying partial-approval semantics (narrator/services/deploy/README.md, Agent Validation).
6. An alarm activation carries acknowledged/resolved/cleared/discarded as independently nullable timestamps rather than a single status enum, so the same underlying question keeps recurring across the platform: can an alarm re-fire for the same underlying condition while a prior activation of it is still open, and can it be acknowledged after being cleared (ux-services/services/front/design/alarm_activations.go:39-63)?
7. A site can be on two live control-config authoring systems at once (classic CAML vs the newer "narrator" system), and every consumer of alarm/setting/deployment data is built to not need to know which one is authoritative for a given site — the abstraction boundary is deliberately load-bearing (ux-services/services/front/design/control_config.go:17-30; alarm-presentation README).
8. Refresh tokens can be revoked out-of-band by the identity provider (Auth0) without the platform's own record of them being updated, and the team has an open, unresolved TODO about it: "There can be cases when the token would get automatically revoked by Auth0... What should we do about those tokens?" (iam/services/refresh-token/README.md, TODO section) — a two-store staleness problem the team has explicitly flagged as unsolved rather than modeled away.
9. An invitation's expiry is a predicate checked lazily against wall-clock time rather than an event fired by a timer, and a still-usable invitation can be "un-expired" by resending it — so "expired" is not a one-way absorbing state the way it would be under a push-based TTL model (iam/services/invitation/design/design.go:118,159-160).
10. A cluster's deployed version can be frozen against the platform's own automation via a `*_LOCK` file while every other cluster keeps auto-updating — so "rollout" is not global-in-lockstep, it's per-cluster and can silently diverge for however long the lock stays in place (cloud-state/README.md, Version Management System).
11. An onsite atlas client keeps operating and caching data through a network outage, and is expected to reconcile once connectivity returns — but the read materials never specify what happens if the cloud's desired state changed more than once during the outage (legacy/README.md, Atlas Client section).
12. A blueprint or CAML source can be compared as "draft vs a specific version" or "version vs version," and a dedicated Differ service exists purely to answer "what changed between these two," which implies the underlying representations are expected to diverge routinely enough to need a standing comparison tool rather than an occasional migration script (ux-services/services/differ/design/design.go:10-42; narrator also has its own `differ` service).
13. A command sent to an agent is retried across every currently-open stream for that agent (multiple concurrent connections are explicitly supported for redundancy), which raises an implicit at-least-once/deduplication question the docs don't address: what stops the agent from executing the same forced-value or setting command twice (facility-status/EXECUTIVE_SERVICE_DETAILED.md, Architecture and Design; `push_command`).
14. Publishing a UAT result or a blueprint draft is a one-way door — once published, a version number is assigned and the content "can no longer be updated" — so the mutable-draft / immutable-published-version split recurs as its own recurring situation distinct from the general deploy workflow (ux-services/services/front/design/uat-orchestrator.go:76-77).
15. A scheduled application carries three independently-settable booleans rather than one status — enabled/disabled, scheduling-capability enabled/disabled (settable separately for the application and for an individual scheduled reading), and shown/hidden from the UI — and the design explicitly states that hiding an application does not disable its scheduling ("Application will still participate to agent schedule" while hidden), so a combination like hidden-but-still-running is intended, and the interesting bugs are the combinations nobody intended (ux-services/services/front/design/scheduling.go:92-93,110-132,382,425-426).
16. A cluster's deploy concurrency is scoped per-entity rather than global: two deploys to the same cluster must never interleave, but deploys to different clusters are meant to run at once, and the mechanism for keeping that true is a naming convention (a concurrency-group key built from the cluster name) rather than a lock the deploy logic itself acquires and releases (cloud-state/.github/workflows/deploy.yaml:42-44).
17. A Kinesis consumer's forward progress depends on checkpointing at the right moment — after a batch, and again on a `TERMINATE` shutdown — and the code comment treats getting this wrong as fatal to the consumer rather than merely lossy, which makes checkpoint-then-crash and crash-then-checkpoint two distinct failure windows worth telling apart (legacy/pkg/server/common/base_processor.go:41-63).

## 3. What this platform has that a generic backend doesn't

- **A physical facility that exists independent of what any service believes about it.** Sensor readings, forced overrides, and control states aren't just database rows — they correspond to real HVAC/electrical equipment that keeps running (or fails) whether or not the software agrees on its state. This is why "current value vs desired value" (settings) and "reported control state vs actual controlling hardware" (control-state) are load-bearing distinctions rather than incidental caching details: the software's model can be wrong about the world in a way a typical CRUD backend's model cannot.
- **Real-time, safety-adjacent control loops running at the edge, disconnected from the cloud by design.** The atlas client is explicitly built to keep operating — and to keep controlling physical equipment — through a network outage (legacy/README.md). A generic backend degrades to "requests fail"; here, degraded connectivity means an autonomous control loop is making decisions the cloud hasn't seen yet, and reconciliation on reconnect is a first-class problem, not an edge case.
- **A negotiated handoff of authority, not just a data write.** The three-way agent-approval gate before a deployment is "accepted" (narrator deploy flow) reflects that the cloud cannot simply push new control logic onto a facility; the agent must actively validate it can run safely on the hardware it actually has before authority transfers. That's a workflow shape a stateless web API rarely needs.
- **Physical overrides that must expire back to automatic control.** Force-point TTLs exist because a human manually overriding a valve or setpoint is inherently a temporary, safety-relevant exception — the system must not let a forgotten override become permanent. A generic backend's "temporary flag" rarely carries this kind of consequence if it silently outlives its intended window.
- **Split-brain over which computer is allowed to touch physical equipment.** The Multiple-Primary Alarm exists because two nodes both believing they are `controlling` the same facility is a safety hazard, not merely a data-consistency nuisance — the alarm is a detection mechanism for a scenario the system can't fully prevent.

## 4. Absent or rare shapes

- **`resource` (quota / rate-limit / capacity)** is essentially absent from the design layer across all six directories surveyed — no admission control, no rate limiting, no capacity bound was found in any README or Goa design file (grep across `services/` in facility-status, ux-services, iam, narrator turned up nothing for `quota`, `rate.?limit`, `RateLimit`, `Capacity`). What superficially resembles it (force-point counts) is an inventory of overrides, not a limit being enforced.
- **`delivery`** is present at the transport layer (streams, Kinesis, synchronous acked commands) but is documented as an operational property rather than as an explicitly modeled guarantee — no README states an ordering or dedup invariant the way the invitation state machine states its transition guards. A practice set drawing from here should treat delivery scenarios as inferred from the transport description, not as directly attested claims.
- **`concurrency`** in the classic sense of "two operations racing on the same record" is under-documented relative to how often it's structurally implied (multi-stream command delivery, multi-instance settings updates, multi-primary control). Two places name it outright — the control-state alarm and cloud-state's per-cluster deploy concurrency group — but both are infrastructure-level (a domain alarm, a CI grouping key), not a stated invariant over application state; elsewhere it has to be inferred from architecture descriptions.

## Yardstick

The five shapes a practice set for this engineer should weight most heavily, in order:

1. **workflow** — his own platform's hardest bugs live in multi-step, multi-party sequences with real abort branches (the narrator deploy flow's three-way agent approval, invitation's per-status-guarded transitions), not in single-step CRUD.
2. **two-store** — the cloud/edge split is structural here, not incidental; "two places must agree, and one of them can go dark" is closer to this platform's default condition than its exception.
3. **lifecycle** — nearly every named entity (alarm, invitation, deployment, control state, draft) is a state machine with informally-stated guards, and the recurring bug shape is a forbidden or under-specified transition slipping through.
4. **expiry** — TTLs and lease-like reconfirmation appear at both the millisecond and day timescale, and at least one of them (invitation expiry) is checked lazily rather than pushed, which is exactly the kind of subtlety that produces real bugs.
5. **rollout** — cloud-state's entire purpose is versioned rollout across a fleet with per-cluster locks and branch overrides, and narrator/ux-services layer their own site-level versioning on top of it, so this shape is both wide (many services) and deep (multiple independent rollout mechanisms stacked on each other).

`concurrency`, `delivery`, and `resource` are real but secondary: concurrency shows up mostly as a named failure mode to detect after the fact rather than a mechanism the docs walk through in depth, delivery is described operationally rather than as a checked invariant, and resource/quota is essentially unattested in this codebase.
