# Isolation without the database: spike report

Date: 2026-09-06. TLC2 Version 2026.07.31.184830 (`tlc` with no arguments, line 1).

The survey scored the whole isolation family under framing (b), then said the framing
itself was untested: "Framing (b) works only if the model can express 'the scheduler may
do anything read-committed permits' without modelling read-committed's mechanism. That is
a real modelling question I have not tested. It is the thing to spike first."
(`.claude/overnight-2026-09-06/survey/semantics.md:1067`)

This is that spike. Short answer: framing (b) works for serialisable, snapshot isolation
and read committed. The isolation rules fit in one module of 28 to 43 lines of code, the
application is written once and runs unchanged against all three, and the write-skew
counterexample lands in 21 states and half a second. The mechanism does come back at read
uncommitted, and I didn't build that level. Details below.

## What I built

Six modules, split into a given half and a learner half.

| file | role | code lines | defs | variables |
|---|---|---|---|---|
| `IsoSerial.tla` | given, serialisable | 35 | 9 | 4 |
| `IsoSnapshot.tla` | given, snapshot isolation | 43 | 10 | 5 |
| `IsoReadCommitted.tla` | given, read committed | 28 | 9 | 3 |
| `OnCallSerial.tla` | application, write skew | 31 | 13 | 1 |
| `LostUpdateSerial.tla` | application, lost update | 27 | 12 | 1 |
| `ReadSkewSerial.tla` | application, read skew | 55 | 19 | 2 |

Counts from the command in "Re-running the numbers" below. Code lines exclude blank lines,
`\*` lines, `(* *)` blocks, and the module header and footer rules.

Each of the three applications exists in three copies, one per isolation level. The copies
are generated by `sed` from the serialisable one, so identity is a property of how they
were made rather than a claim about how careful I was.

The API the given half exposes, and the whole of it:

- `IsoInit(s0)` sets the committed store to `s0`
- `IsoVars` is the tuple of scaffolding variables
- `Begin(t)`, `Running(t)`, `See(t, k)`, `Put(t, k, v)`, `Idle`, `Finish(t)`

`See` is a state function, not an action. That turns out to matter, and I come back to it
under "Where it leaks".

## The ladder is real, and one anomaly can't show it

Verdicts by application and level, from the `rc` column above:

| application | serialisable | snapshot | read committed |
|---|---|---|---|
| write skew (on call) | 0 | 12 | 12 |
| lost update (counter) | 0 | 0 | 12 |
| read skew (report) | 0 | 0 | 12 |

Write skew alone doesn't separate snapshot isolation from read committed. Both permit it,
so both exit 12. It takes a second application to pull them apart. I think that's the more
useful finding of the two, because it answers the brief's question about whether the ladder
is different models or different constants. It is neither. The level is a different
scaffolding module, the anomaly is a different application module, and the fixture size is
a constant. Three separate axes, and the brief's ladder lives on two of them.

Lost update and read skew both separate the same pair, but they exercise different halves
of the snapshot-isolation module. Lost update is stopped by first-committer-wins, which is
`NoConflict` in `IsoSnapshot.tla:71`. Read skew is stopped by the read snapshot, which is
`snap` in `IsoSnapshot.tla:60`. So both rules are load-bearing and each has an application
that observes it on its own.

## Does the model agree with the databases

The oracle is Hermitage. Downloaded 2026-09-06:

```
curl -sS -o hermitage-postgres.md \
  https://raw.githubusercontent.com/ept/hermitage/master/postgres.md   # 314 lines
```

Postgres "repeatable read" is snapshot isolation, so its column is the one to compare
against `IsoSnapshot`. Six rows, all matching:

| anomaly | Hermitage says | my model says |
|---|---|---|
| P4 lost update | read committed does not prevent (`postgres.md:154`) | `LostUpdateReadCommitted` rc 12 |
| P4 lost update | repeatable read prevents (`postgres.md:167`) | `LostUpdateSnapshot` rc 0 |
| G2-item write skew | repeatable read does not prevent (`postgres.md:244`) | `OnCallSnapshot` rc 12 |
| G2-item write skew | serializable prevents (`postgres.md:257`) | `OnCallSerial` rc 0 |
| G-single read skew | read committed does not prevent (`postgres.md:184`) | `ReadSkewReadCommitted` rc 12 |
| G-single read skew | repeatable read prevents (`postgres.md:199`) | `ReadSkewSnapshot` rc 0 |

The failure mode also matches. Hermitage's P4 trace at repeatable read ends with
"T2 now prints out ERROR: could not serialize access due to concurrent update"
(`postgres.md:176`), and `IsoSnapshot.Finish` moves the transaction to `aborted` in the
same situation. Probe `probe-d-abort.cfg` confirms that branch fires.

Six rows out of the thirty the family could supply. That's the honest denominator and it's
small. What it does establish is that the rules I wrote aren't a private invention that
happens to reproduce one anomaly.

### The counterexample, watched

`OnCallSnapshot` at states 5 through 7, the interesting end of the trace:

```
State 5: <DoFinish("alice")>
/\ state = [alice |-> "committed", bob |-> "running"]
/\ store = [alice |-> "off", bob |-> "on"]
/\ snap  = [ alice |-> [alice |-> "on", bob |-> "on"],
             bob   |-> [alice |-> "on", bob |-> "on"] ]

State 6: <DoCheck("bob")>
/\ wset = [alice |-> [alice |-> "off"], bob |-> [bob |-> "off"]]

State 7: <DoFinish("bob")>
/\ store = [alice |-> "off", bob |-> "off"]
```

Bob's snapshot still shows both doctors on call after Alice committed, so Bob's check
passes. The write sets are disjoint, so first-committer-wins lets him through. Nobody is
on call. That is write skew and nothing else.

I watched the other two failures the same way. `LostUpdateReadCommitted` ends with
`store = [counter |-> 1]` and both transactions committed, which is Hermitage's P4.
`ReadSkewReadCommitted` ends with `seen = [reader |-> [a |-> 10, b |-> 15]]`, a total of 25
against a real total of 20, which is Hermitage's G-single.

## How much of it is scaffolding

Both numbers, because they say different things.

**By line, the split is close to even.** Against `IsoSnapshot` at 43 code lines, the
on-call application is 31, the counter is 27, and the report is 55. So the scaffolding is
58%, 61% and 44% of its model. Against `IsoReadCommitted` at 28 lines it drops to 47%, 51%
and 34%. Nothing here is nine tenths.

**By variable, the split is bad.** Snapshot isolation declares 5 variables and the on-call
application declares 1. So 83% of the state is scaffolding, and 71% on the read-skew model
which declares 2. If you judge framing (b) by how much of the state space the learner
authored, it fails.

I think the line count is the number that matters and the variable count is the one that
looks alarming, so here's why I'd weigh it that way. The five scaffolding variables are the
same five in every problem in the family. The learner never declares them, never
initialises them, and never writes an action that touches them except through the six-name
API. They aren't representation choices the learner is making badly. They're the platform.

The count that settles it is the third one. One scaffolding module served three
applications with no edits, and the applications are 31, 27 and 55 lines. So across the
family the scaffolding is 43 lines against 113, which is 28%, and it goes to zero the
moment it's handed over.

## Could the scaffolding be given to the learner

Yes, and the evidence is that I already did it three times without meaning to test that.

Each application was written once against `IsoSerial` and then generated for the other two
levels by substituting two tokens. The diff:

```
$ diff OnCallSerial.tla OnCallSnapshot.tla
1c1
< --------------------------- MODULE OnCallSerial ---------------------------
---
> --------------------------- MODULE OnCallSnapshot ---------------------------
16c16
< EXTENDS IsoSerial, Sequences
---
> EXTENDS IsoSnapshot, Sequences
```

Two lines, one of which is the module name. The same diff holds for the read-committed copy
and for all four `LostUpdate` and `ReadSkew` pairs. The `.cfg` files are byte identical
across levels, and `cmp` reported no difference on either set.

So the given part is one `.tla` file per isolation level, and the learner's job is a module
that extends it. The problem statement hands over:

- the three `Iso*.tla` modules, unmodifiable
- the six-name API and what each name means
- the `.cfg` skeleton with `Key`, `Txn` and `Value` left to fill

The learner writes `Init`, the transaction's steps, `Next`, `Spec`, and the invariant. On
the on-call problem that's 13 definitions and one variable. The isolation level then becomes
a single-token choice on the `EXTENDS` line. That's a good shape for a problem that wants
the learner to feel the level as a decision rather than as a topic.

There's a real design decision buried in the API and it's worth flagging for whoever writes
the problem set. `See(t, k)` reads like an expression, so a transaction body reads like the
SQL it stands for. The cost is in the next section.

## Where it leaks

Three places. The first two are bounded and I'd ship anyway. The third is the boundary of
the framing.

**Serialisable is modelled as serial, which hides the retry.** `IsoSerial` lets one
transaction run at a time, so `Finish` never fails. Real serialisable aborts you instead,
and Hermitage's own trace says so: "ERROR: could not serialize access due to read/write
dependencies among transactions" (`postgres.md:267`). Serial execution is sound for
checking a safety invariant, because a serialisable execution leaves the committed store
where some serial execution leaves it. It isn't sound for what the application has to
handle. A learner who models serialisable this way will conclude, correctly, that their
invariant holds, and will never meet the retry loop they need in production. Fixing it
means detecting non-serialisable outcomes, which needs the dependency graph, which is
framing (a). I'd state the limit in the problem text rather than fix it.

**Read committed omits write-write blocking.** Hermitage's P4 trace has T2 "BLOCKS" on the
row lock (`postgres.md:162`) and my model just lets both writes buffer. Blocking changes
when a step may happen, not which committed states exist, so the safety verdicts are
unaffected. What it does cost is the database-side atomic update. `UPDATE t SET v = v + 1`
under read committed re-reads the row after it unblocks, and doesn't lose the update. My
model can't express that, because `Put` takes a value rather than a function. Adding it is
one more operator in the given part. I have not built it, so treat the cost estimate as
a guess.

**Read uncommitted is where the mechanism comes back, and I didn't build it.** At every
level I did build, "the store" and "the committed store" are the same object. That's why
`store` can be a single variable and the invariant can be a predicate over it. Read
uncommitted is defined by those two coming apart. To model it you have two routes. Put
uncommitted writes into `store` and carry an undo log, which breaks every application
invariant that reads `store`. Or make `See` consult other transactions' write sets, which
needs an order over concurrent writers to stay deterministic. Both are a version pointer
wearing a different hat. `INFERRED` for the whole paragraph, since I stopped before building it.

The related point is that read uncommitted isn't visible with the three applications I
have. The anomalies that separate it from read committed are G1a and G1b, and both need a
rollback the application can trigger. So the fourth rung costs a new operator in the given
part and a new application, not just a new `Iso*` module. `INFERRED`

## Three things the tools did that I didn't expect

**TLC warns about the subscript and the warning is cosmetic.** Every run prints "The
subscript of the next-state relation specified by the specification does not seem to
contain the state variable" once per variable. `vars` is a tuple concatenation and TLC's
static check doesn't see through the concatenation operator. I wrote
`ProbeExplicitVars.tla`, identical apart from an explicit six-name tuple, and it produced
27 generated, 21 distinct, depth 7, rc 12. Those are `OnCallSnapshot`'s numbers to the
digit, and the warning count went from 5 to 0 under
`grep -c 'does not seem to contain the state variable'`. I kept the concatenation because
it's what keeps the three application copies identical, but a learner-facing version of
this should probably take the warning-free form and give up the byte identity.

**`spike-measure.sh` reports 1 variable for a 6-variable model.** Covered above. The tool
is right about the module and wrong about the model.

**A probe loop silently ran nothing, and the shell was the reason.** `for pair in "a b"`
then `set -- $pair` doesn't word-split under zsh. TLC got one argument named
`"probe-a-off.cfg ProbeSerial"` and exited 1 on all four probes. rc 1 isn't in
`spike-measure.sh`'s verdict table, which is what made me look. Worth knowing for any
harness code in this repo that loops over pairs.

## Where I disagree with the brief

Two places, neither of them large.

The brief says the reference model "reportedly needs on the order of 405 million states and
a twelve-step trace". Both numbers are in the source and they describe different things.
The README's own TLC output reads "529068865 states generated, 405673796 distinct states
found" and "The depth of the complete state graph search is 13", with the trace running to
State 12
(<https://raw.githubusercontent.com/will62794/snapshot-isolation-spec/master/README.md>,
fetched 2026-09-06). So it's 405.7M distinct at depth 13, and 12 states of trace. The
brief's summary is fair.

The brief asks whether read committed "actually shows up as different models rather than
different constants". It does, but the question has a hidden third option the answer needs.
It's different modules on two axes, level and application, with the constants as a
separate size knob. Write skew alone would have made read committed look like it adds
nothing.

## Verdict

Framing (b) is viable and I'd build the family on it. Taking the isolation level as given
doesn't smuggle the mechanism back in for serialisable, snapshot isolation or read
committed. Those three levels are 28 to 43 lines of code and 3 to 5 variables each, with no
versions, no timestamps, no logical clock and no history in the state, and they reproduce
six Hermitage rows correctly. The evidence that they're given rather than entangled is that
three applications ran against all three levels with a two-line diff per copy, one line of
which is the module name. The size difference against framing (a) isn't marginal.
`will62794/snapshot-isolation-spec` is 619 lines with 58 definitions, and it needs
405,673,796 distinct states at depth 13 over 64 minutes to reach a read-only anomaly. My
write-skew counterexample is 21 distinct states at depth 7 in half a second. The reason is
that the property is the application's own invariant over a two-key store, not a
serializability check over a history variable. The costs are real and I'd write them into the problem text rather
than pretend they aren't there. Serialisable modelled as serial hides the retry the
application actually owes, read committed without row locks can't express a database-side
atomic update, and read uncommitted is where the store and the committed store come apart
and the mechanism has to come back. Three rungs out of four and three anomalies out of ten,
so I'd want two more applications built before calling the family proven rather than
promising.
